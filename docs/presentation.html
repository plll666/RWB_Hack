Почему не одна широкая таблица?

У заказа, позиции, платежа и отзыва — разная гранулярность.
Прямой join позиций с платежами размножает строки и суммы: сначала агрегируем каждый факт до заказа, потом сверяем.

2 сущности покупателя: buyer — человек по customer_unique_id (96 096) · customer_record — адресная запись по customer_id (99 441)
Восемь CSV загружаются без изменений в raw; типизация и связи появляются в core; запросы ответов используют только core. Разные факты нельзя бездумно объединять: позиции и платежи имеют гранулярность строк факта. Устранение размножения — предварительная агрегация отдельно. buyer — постоянный человек, customer_record — запись клиента/адреса.
9 таблиц core: каждый факт на своём уровне
Справочникиbuyer · customer_record · seller · product · product_categoryсвойства сущностей отдельно от продаж
ordersPK order_idдаты жизненного цикла: purchased → approved → carrier → delivered
order_itemPK (order_id, order_item_id)цена и доставка позиции; order_item_id уникален лишь внутри заказа
order_paymentPK (order_id, payment_sequential)отдельный факт: платеж может быть не один
order_reviewPK review_row_id (IDENTITY)исходный review_id не уникален — дубли не удаляем
ОграниченияPK + FK + типыnumeric(12,2) · timestamp · NULLIF для пустых · позиции и платежи нельзя join напрямую
Объясните девять core-таблиц через назначение и гранулярность: buyer, customer_record, seller, product, product_category — справочники; orders, order_item, order_payment, order_review — сущности и факты с ключами и связями. Отзывы сохраняются построчно с техническим ключом, так как review_id повторяется.
build.sql: полная пересборка в одной транзакции
1 · Порядок

BEGIN → создание схемы →
DROP CASCADE от фактов
к справочникам →
raw не трогаем
2 · Перенос

INSERT … SELECT из raw:
text → timestamp,
размеры → integer,
деньги → numeric(12,2)
3 · Защита

PK/FK не дают ссылке
висеть в воздухе,
индексы для join и дат,
в конце — COMMIT
Полная пересборка, не инкремент — тот же скрипт даёт тот же результат повторно.
Ошибка приведения типа или ограничения откатывает транзакцию: наполовину собранного core не бывает.
Аномальные даты не переставляем: NULLIF превращает пустые в NULL, а диагностика — зона checks.sql
build.sql повторяемо пересоздаёт core в транзакции. Данные переносятся через INSERT SELECT, типы преобразуются; PK/FK защищают модель. Деньги хранятся в numeric. Пустые даты остаются NULL; временные аномалии не переставляются автоматически. Сейчас полная пересборка достаточна для примерно 550 тысяч строк.

Дашборд — концепция для руководителя операций. Он отвечает, где меняются продажи, какие продавцы и категории требуют внимания и где возникают задержки. Источник показателей — core, определения согласованы с контрактом участника 1. Продажи, статусы и сроки показываются на соответствующем уровне фактов.

Честные границы: неаддитивность и качество данных
Нельзя складывать между срезами
Средний чек · средние сроки · медианы · доли статусов и опозданий · уникальные покупатели — пересчитывать из базовых строк или числитель/знаменатель
Данные кончаются, и мы это показываем
Период до окт. 2018 · не у всех заказов есть отзыв · платежи расходятся с корзиной · только статус-срез, без истории смен статусов
Правило честности: рядом с каждой метрикой доставки — число заказов, вошедших в расчёт. Корреляция задержки и оценки — не доказательство причинности.
raw → core → mart · контракт метрик · автоматические проверки · модель готова к вопросам, которых ещё нет
Доли, средние, медианы и уникальные покупатели неаддитивны — для нового среза их нужно пересчитывать по базовым числителям и знаменателям. Период ограничен октябрём 2018, а источник содержит пропуски и не хранит историю смены статусов. Рядом с метрикой доставки показываем число заказов в расчёте; связь задержки с оценкой не доказывает причинность.
