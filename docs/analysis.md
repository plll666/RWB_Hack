# Полный анализ данных Capibara / Olist

Дата выполнения: 28 октября 2026. Проверка проведена на локальной копии репозитория, загруженной в PostgreSQL 16. Исходные строки в `raw` не менялись.

## 1. Краткое резюме

- Загружено **550 759 строк** из восьми CSV; диапазон оформления заказов — **2016-09-04 — 2018-10-17**.
- Базовые факты: 99 441 заказ, 112 650 позиций, 103 886 строк платежей и 99 224 отзыва. Связи по идентификаторам не потеряли ни одной строки дочерних таблиц при проверке на сиротские ключи.
- 96 478 заказов помечены как `delivered` (**97,02%**). Статус доставки и заполненность временных отметок — разные вещи: у небольшой части заказов с этим статусом не хватает одной из дат.
- Для пяти вопросов кейса контрольные ответы сошлись: товарная выручка **13 221 498.11**, средний чек с доставкой **159.88**, **96 096** постоянных покупателей, повторная покупка у **2 997** (3,12%), **74** категории.
- Главные методологические риски: неверная гранулярность соединений, использование неправильного ключа покупателя, смешение оплаты с выручкой, отбрасывание пустых месяцев и слияние категорий без перевода в одну.

## 3. Связи и гранулярность

```text
buyer (customer_unique_id) 1 ── * customer_record (customer_id) 1 ── * orders
orders 1 ── * order_item * ── 1 product ── 1 product_category
orders 1 ── * order_item * ── 1 seller
orders 1 ── * order_payment
orders 1 ── * order_review
```

`order_item_id` — порядковый номер внутри заказа, а не количество товара и не глобальный ID. В CSV нет отдельной колонки количества; в расчётах кейса строка позиции считается одной единицей.

Один заказ может иметь несколько товарных позиций и несколько платежей. Нельзя напрямую соединить `order_items` с `order_payments` и затем суммировать суммы: каждая позиция размножится на число платежей. При необходимости сравнить их сначала агрегируйте обе таблицы до одного ряда на заказ.

Проверки ссылочной целостности дали ноль строк без соответствующего заказа, товара, продавца или клиентской записи: все 112 650 позиций, все платежи, все отзывы и все заказы находят родительские записи.

### Несогласованности и особые случаи

- В четырёх карточках товара вес равен нулю; диапазон непустых весов — 0–40 425 г. Перед логистическими расчётами нулевой вес нужно проверять или маркировать как неизвестный.
- В 166 заказах время передачи перевозчику раньше времени оформления; в 23 — вручение раньше передачи перевозчику. Не исправлять автоматически: сохранять исходные даты, помечать аномалию и уточнять правило у владельца данных.
- Среди заказов со статусом `delivered` есть 2 без даты передачи перевозчику и 8 без даты вручения. Для расчёта времён доставки использовать только строки с нужными отметками, а полноту показывать рядом с метрикой.
- **775 заказов не имеют товарных позиций**: 164 `canceled`, 603 `unavailable`, 1 `shipped`, 2 `invoiced` и 5 `created`. При этом в данных платежей есть 99 440 из 99 441 заказов. Один заказ со статусом `delivered` не имеет строки платежа.
- Из 73 непустых исходных категорий у 71 есть перевод. `pc_gamer` и `portateis_cozinha_e_preparadores_de_alimentos` без перевода; их нужно оставить разными категориями, не сливать в `Unclassified`. Ещё 610 продуктов имеют действительно пустую категорию.

## 6. Деньги, выручка и оплаты

### Определения для ответов кейса

Для контрольной метрики выручки использована **стоимость товаров без доставки**: сумма `price` только по строкам заказов со статусом `delivered`. Доставка учитывается отдельно как `freight_value`. Это правило даёт контрольные **13 221 498.11** за окно оформления `[2016-09-01, 2018-09-01)`.

Средний чек заказа, напротив, включает товар и доставку. Сначала строится один итог на заказ (`sum(price + freight_value)`), затем берётся среднее по доставленным заказам окна. Результат — **159.88**. Нельзя усреднять цену строки или считать чек из строки платежа: это другая гранулярность.

### Общие суммы и типы оплат

За все позиции выгрузки сумма цены — **13 591 643.70**, сумма доставки — **2 256 599.44**, вместе — **15 848 243.14**. Это не должно автоматически равняться сумме платежей: есть заказы без позиций, заказы без платежей и индивидуальные расхождения. Среди 98 665 заказов, где присутствуют обе стороны, 366 отличаются более чем на 0.01; максимальное абсолютное отклонение — 336.93. Это контроль качества и повод исследовать статусы/механику расчёта, а не основание подменять один показатель другим.

Цена позиции: среднее **120.65**, медиана **74.99**, максимум **6 735.00**. Для аналитики средний чек рассчитывается на заказе; эти line-level числа полезны только как профиль позиции.

## 11. Модель данных и воспроизводимость

`model/build.sql` собирает `core` из `raw` в транзакции и повторно выполняется без ручной очистки. Модель хранит отдельные факты `orders`, `order_item`, `order_payment`, `order_review`; справочники `buyer`, `customer_record`, `seller`, `product`, `product_category`. `model/answers.sql` отвечает на первые пять вопросов только через `core`.

Особые решения модели:

1. `buyer` использует постоянный `customer_unique_id`; `customer_record` сохраняет адресную запись и связывает её с заказом.
2. Позиция заказа имеет составной ключ (`order_id`, `order_item_id`). Платёж имеет (`order_id`, `payment_sequential`).
3. Отзывы сохраняются построчно с техническим ключом, потому что `review_id` повторяется между заказами.
4. Типы приводятся в core; пустые временные отметки остаются `NULL`. Некорректные временные последовательности не «чинятся» автоматически.
5. Категории без перевода остаются раздельными; только пустое исходное значение уходит в отдельную `Unclassified`.
6. Денежные значения представлены `numeric`, а не `float`, чтобы округление не меняло суммы.

Проверено на PostgreSQL 16: повторная сборка завершилась, `core` сохранил ожидаемые количества строк, контрольные ответы совпали, внешние ключи не теряют записи.

```bash
bash scripts/setup.sh
docker exec -i hack_postgres psql -U hack -d marketplace -v ON_ERROR_STOP=1 -f - < model/build.sql
docker exec -i hack_postgres psql -U hack -d marketplace -v ON_ERROR_STOP=1 -f - < model/answers.sql
```

## 12. Дашборд и дальнейшие шаги

### Концепция дашборда: продажи и исполнение заказа

Аудитория — руководитель операций и категорийные менеджеры. Основные показатели: заказы и товарная выручка по месяцу оформления; продажи по категории и продавцу; доля delivered/canceled/unavailable; срок передачи перевозчику; срок вручения относительно обещания; повторные покупатели.

- Выручка: сумма `item_price` по доставленным заказам; уровень позиции, затем агрегация по периоду/категории/продавцу.
- Средний чек: сумма `item_price + freight_value` внутри заказа, затем среднее по заказам.
- Доля доставки вовремя: число заказов, вручённых до обещанной даты включительно, делённое на число доставленных заказов с обеими датами.
- Повторные покупатели: покупатели с более чем одним заказом / все покупатели в выбранной когорте.

Средний чек, доли статусов, доля опозданий и доля повторных покупателей — **неаддитивные** показатели. Их нельзя суммировать между месяцами или категориями; при объединении срезов надо пересчитывать числитель и знаменатель из базовой гранулярности.

### Развитие

1. Добавить проверки качества на дубликаты естественных ключей, сиротские связи, некорректный порядок времён, пересогласование оплат и корзины, нулевой вес и доли пропусков.
2. В текущем `orders` есть временные отметки, но нет полной истории смены статусов. Для SLA и аудита нужен отдельный журнал событий с `order_id`, статусом, `occurred_at`, временем поступления в хранилище и источником.
3. Зафиксировать историчность карточек товара и продавца, если нужны отчёты «как было на момент заказа»; текущие справочники отражают только состояние выгрузки.
4. Текущие 550 тыс. строк PostgreSQL обрабатывает без проблем. Первым ограничением при росте станет полная пересборка и конкуренция ETL с аналитическими запросами. Следующий шаг — инкрементальная загрузка и пакетное обновление витрин. При существенно большем объёме и параллельных тяжёлых отчётах рассмотреть колоночное аналитическое хранилище, оставив PostgreSQL для источника/операционных данных.
