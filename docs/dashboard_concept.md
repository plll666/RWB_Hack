# Концепция дашборда

> Реализация — **FastAPI (`backend/`) + React/Vite (`frontend/`)**, дизайн
> продолжает проверенный мок (`dashboard-mock/`)

## Архитектура

```
PostgreSQL (core + mart)
        │  параметризованные SELECT (%s), только core/mart
FastAPI  backend/main.py + backend/queries.py   ← /api/overview|delivery|categories|product|quality|meta
        │  JSON, порты: 8000 (proxy /api из Vite)
React    frontend/src/  (Vite dev :5174, build/preview :4173)
```

- **Слой данных** — один: `backend/queries.py`. Все обращения к БД идут
  через `backend/db.py` (пул psycopg2, DSN из `DATABASE_URL`, фоллбек
  5433 → 5432). Никаких обращений к `raw`, никакой склейки SQL-строк.
- **Фронтенд не содержит бизнес-логики**: считает только пресеты дат и
  форматирует числа; каждое число на экране приходит из SQL-запроса.
- Эксплуатация и команды запуска — `docs/dashboard_usage.md`.

## Кто пользователь и какое решение он принимает

Отдел операций маркетплейса. Он не читает SQL: он открывает исторический
дашборд, находит срез, где продажи или доставка просели, и передаёт действие —
менеджеру список проблемных продавцов (ID копируется из таблицы
кнопкой), логистике регион и масштаб задержки. Это **аналитика исторической
выгрузки Olist до октября 2018**: никаких онлайн-уведомлений, автоподстройки
сроков и причинных выводов дашборд не обещает.

## Четыре вкладки

1. **Обзор** — KPI-полоса: заказы (все статусы), товарная выручка
   (доставленные, без доставки), средний чек (`full_ticket`), доля
   доставленных вовремя с видимым знаменателем; помесячная динамика на
   SVG-графике (два ряда: заказы слева, выручка млн R$ справа; месяцы без
   заказов не исчезают; кроссхейр-тултип) и распределение статусов
   (сумма долей = 100%).
2. **Доставка** — среднее и медианное время, доля опозданий, число заказов
   в расчёте; таблица штатов с порогом ≥ 500 заказов (как в вопросе 7,
   порог перенастраивается в интерфейсе); связь оценки 1–5 со сроком и
   опозданием (как в вопросе 10, уникальные пары заказ/оценка).
   Подпись: ассоциация, не причинность.
3. **Категории и продавцы** — выручка на уровне позиции, заказы через
   `count(distinct order_id)`; таблицы с копируемыми идентификаторами;
   история цен товара из вопроса 6 (дата, цена, единицы) с дефолтным
   чемпионом по числу разных цен из `GET /api/product/champion`.
4. **Качество данных** — период снимка, счётчики записей каждого уровня,
   пропуски дат, заказы без позиций, расхождения платежей и корзины.
   Значения считаются запросами к `core`/`mart`, констант нет; смысл
   PASS/WARN из `model/checks.sql` объяснён на экране.

## Фильтры

- **Глобальные:** диапазон даты оформления и исторический штат покупателя
  (выпадающий список с чекбоксами). Действуют на все вкладки; пресеты
  («Весь период», «2018», «2017», «Последние 12 мес.») вычисляются на
  фронте, в SQL уходят только конкретные даты параметрами (`%s`).
- **Локальные:** категория и продавец — только вкладка «Категории и
  продавцы». Так заказовые KPI других вкладок не меняются от локального
  фильтра и не создают двусмысленности.
- Пустой срез любого фильтра — «Нет данных», все вкладки переживают
  пустой выбор без нулевых графиков.

## Контракт метрик

Слой данных дашборда — те же определения, что в `docs/metric_definitions.md`
и `model/answers.sql`:

| Метрика | Формула | Гранулярность |
|---|---|---|
| Заказы | `count(*)` заказов периода, все статусы | заказ |
| Товарная выручка | `sum(item_price)` доставленных заказов | позиция, затем сумма |
| Средний чек | `avg(full_ticket)` = товары + доставка, доставленные с позициями | заказ |
| Доля вовремя | доставленные с полным набором дат, `NOT is_late` | заказ |
| Дни доставки | `delivered_at − purchased_at` в сутках | заказ |
| Опоздание | `delivered_at::date > estimated_delivery_at::date` | заказ |
| Выручка категории/продавца | `sum(item_price)` доставленных | позиция |
| Заказы категории/продавца | `count(distinct order_id)` | заказ |

Витрины-источники: `mart.order_sales`, `mart.order_delivery`,
`mart.sales_item`, `mart.payment_fact`, `mart.review_order` — представления
без материализации, носящие гранулярность фактов `core`. Неаддитивные KPI
(медиана, доли) всегда пересчитываются из строк нужной гранулярности, не
усредняются из заранее посчитанных месячных значений. Контрольные числа для
поверки интерфейса — `docs/answers.md` (выручка 13 221 498,11 R$, средний
чек 159,88, вовремя 89 936 из 96 470, SP 40 494 / 8,76 дн / 4,49 %,
чемпион `437c05a395e9e47f9762e677a7068ce7`).

## Неаддитивность и знаменатели

- Доля вовремя и доля опозданий показываются только вместе с числом заказов
  в расчёте; штат с числом заказов ниже порога (по умолчанию 500) в таблицу
  не попадает — строки скрыты, а не обнулены.
- Средний чек не смешивает заказы без позиций: они не имеют корзины.
- Месячная динамика строится из отдельного календаря: нулевые месяцы видны.
- Тултип графика показывает оба ряда за месяц; правая ось — млн R$.

## Ограничения

- Данные до октября 2018; тег «Исторические данные до 17.10.2018»
  присутствует в шапке (дата — из БД, не константа).
- Дашборд не делает выводов о причинах: связь оценки и срока описательная.
- Пустой срез показывает «Нет данных», а не нулевую выручку.
- Недоступная БД и несобранная модель дают баннер с инструкцией запуска
  (`README`: build → mart → uvicorn), а не пустой график; ошибки SQL
  не маскируются (HTTP 503 с деталями).
