Дата: 28 октября 2026 года. Проверенный коммит: `198d500144a9fa2159423310aa715c6b2ef0c59a`.

## Вывод

Модель и первые пять аналитических ответов соответствуют известным требованиям по гранулярности, ключам и контрольным значениям. ## Состояние Git и границы аудита

- После `git fetch origin` локальная `main` совпадала с `origin/main`, рабочее дерево было чистым.
- Требования сверены по [handout.md](handout.md) и [tasks.md](tasks.md), реализация — по SQL, скриптам загрузки и документам репозитория.

- Во время этого аудита база не пересоздавалась и данные не изменялись. Успешная чистая пересборка схемы `core` и повторная сборка были получены в предыдущем прогоне этого же коммита; они не доказывают успешность полного bootstrap окружения.
- Предыдущие попытки `setup.sh --reset` останавливались на скачивании CSV с `curl: (56) Recv failure: Connection was reset`, до удаления volume. Полный цикл создания окружения и повторной загрузки raw остаётся неподтверждённым.
- В рамках аудита добавлен только этот отчёт; исправления реализации не выполнялись.

## Найденные проблемы

Приоритеты: P1 — исправить до демонстрации/сдачи; P2 — повысить надёжность и точность контроля; P3 — улучшить сопровождение.

### 1. P1: повторный запуск скачивания принимает оборванный CSV за готовый

**Место:** `scripts/download_data.sh:27–32`, `scripts/setup.sh:64–72`.

Скрипт скачивает сразу в конечный файл и при следующем запуске пропускает любой непустой файл (`-s`). После разрыва соединения остаётся непустой частичный CSV. В предыдущих попытках это наблюдалось непосредственно: очередной запуск выводил «уже есть» для неполного файла. Подсчёт восьми имён в setup не проверяет полноту содержимого. `load_raw.py` проверяет заголовок, но не ожидаемое число строк перед commit: усечённый файл, заканчивающийся на целой CSV-записи, может успешно загрузиться. Позднее checks.sql обнаружит недостачу, однако сам setup способен сообщить об успешной загрузке.

**Исправление:** скачивать во временный `.part`, проверять содержимое и только после успешной проверки атомарно переименовывать; удалять неуспешный временный файл. Для фиксированного датасета зафиксировать версию источника и контрольные суммы либо ожидаемые числа CSV-записей. Проверять конкретные восемь имён, а не общее количество файлов.

**Приёмка:** оборвать скачивание, повторить запуск и убедиться, что частичный файл скачан заново; корректный заголовок с неполными данными не должен считаться успешной загрузкой.

### 2. P1: концепция дашборда не полностью закрывает обязательный пункт ТЗ

**Место:** `docs/analysis.md:240–251`, `docs/defense_guide.md:10`.

Концепция уже есть, поэтому считать её полностью отсутствующей было бы неверно. Однако среди заявленных показателей есть доли статусов, срок передачи перевозчику и срок вручения относительно обещания, для которых не приведены полные определения, источники и гранулярность. Роли пользователей названы, но конкретные решения по сигналам дашборда раскрыты слабо. `defense_guide.md` предлагает открыть `docs/dashboard_concept.md`, которого в проверенном коммите нет.

**Исправление:** дополнить существующий раздел или создать отдельный документ. Для каждого показателя указать числитель/знаменатель или формулу интервала, статус и окно дат, базовую гранулярность, таблицы/поля, правила NULL и отрицательных интервалов, аддитивность и управленческое действие. Для доставки в обещанный день явно определить сравнение календарных дат, чтобы время после полуночи не стало ложным опозданием. Исправить ссылку сценария защиты.

**Приёмка:** каждый показатель из перечня можно однозначно реализовать по документу, все ссылки защиты открываются.

### 3. P2: предупреждение о непереведённых категориях завышено

**Место:** `model/checks.sql:229–235`.

Условие `category_label_english = category_id` не означает отсутствие перевода. У категорий `cool_stuff`, `pet_shop`, `consoles_games`, `market_place`, `audio`, `dvds_blu_ray`, `la_cuisine` исходное имя совпадает с корректным переводом.

**Подтверждение SQL:** текущий WARN сообщает **2 058 товаров**. Проверка наличия строки в `raw.product_category_translation` показывает всего **13 товаров без перевода**: 10 в `portateis_cozinha_e_preparadores_de_alimentos` и 3 в `pc_gamer`. Следовательно, **2 045 товаров отмечены ошибочно**.

**Исправление:** сохранять в core признак наличия перевода или исходный nullable-перевод отдельно от отображаемой подписи. Для проверки переноса можно сверяться со справочником raw, но аналитические ответы по-прежнему должны читать core. Разделить количество категорий и количество затронутых товаров.

**Приёмка:** предупреждение показывает две категории и 13 товаров, а совпадающие корректные переводы не включаются.

### 4. P2: отсутствующая метрика может пройти числовую проверку

**Место:** `model/checks.sql:107–166`, особенно проверка `v_health_beauty` на строке 136.

В SQL выражение `abs(NULL - expected) > 0.01` возвращает NULL. В `IF` это не TRUE, поэтому исключение не возникает и далее печатается PASS. Например, если подпись категории `health_beauty` пропадёт, её отфильтрованная сумма станет NULL; количество категорий и общая выручка могут сохраниться, а конкретная проверка лидера будет ложно успешной. Read-only выражение `(abs(NULL::numeric - 1233131.72) > 0.01) IS NULL` в тестовой базе вернуло TRUE.

Кроме того, условие `> 0.01` принимает отклонение ровно на одну копейку, хотя значения фиксированного датасета ожидаются точными.

**Исправление:** для каждой обязательной суммы сначала проверять `IS NULL`; для точных numeric-контролей использовать `IS DISTINCT FROM` ожидаемого значения либо явно описать допустимую погрешность. Для округляемого среднего проверять отсутствие NULL и результат округления.

**Приёмка:** отсутствующая категория и отклонение на копейку вызывают FAIL; корректный срез проходит.

### 5. P2: checks.sql проверяет собственные формулы, а не результат answers.sql

**Место:** `model/checks.sql:79–192`, `model/answers.sql:7–104`.

Формулы дублируются в двух файлах. Ошибка только в answers.sql не изменит результат checks.sql. Финальная проверка `to_regclass` подтверждает лишь существование таблиц, но не доказывает, что ответы читают core, возвращают 24 строки или используют нужные фильтры. Текущие ответы действительно используют core — это подтверждено чтением кода, а не данной автоматической проверкой. Также не проверяются средние позиции/единицы 1.1422 и фактическое первое место `health_beauty` среди категорий.

**Исправление:** создать единые представления/запросы для ответов и проверять их результирующие наборы либо добавить небольшой исполнитель, который запускает именно answers.sql и сверяет результаты. Проверку core-only выполнять анализом зависимостей представлений или разбором SQL, а не наличием таблиц. Добавить проверки 1.1422 и лидера категорий.

**Приёмка:** намеренная ошибка фильтра только в answers.sql обнаруживается автоматическим прогоном.

### 6. P2: локальный Windows checkout не обеспечивает запуск shell-скриптов как в README

**Место:** `scripts/setup.sh`, `scripts/download_data.sh`, README.

`git ls-files --eol scripts/*.sh` показывает `i/lf w/crlf`; локальный `core.autocrlf=true`, `.gitattributes` отсутствует. В предыдущем запуске WSL Bash выдавал `$'\r': command not found` и ошибку `pipefail`. Это проблема переносимости checkout, а не ошибка SQL-модели. Выбор первого `python3` в PATH также может взять WSL/MSYS-интерпретатор без pip вместо установленного Windows Python. README содержит Bash-перенаправление `<`, которое нельзя исполнять напрямую в PowerShell.

**Исправление:** зафиксировать LF для `*.sh` в `.gitattributes`, описать поддерживаемый Bash и виртуальное окружение, разрешить явный выбор Python. Для Windows привести рабочий сценарий Git Bash/WSL или отдельные PowerShell-команды.

**Приёмка:** свежий clone на Windows со стандартным autocrlf запускается по инструкции без ручной правки переносов строк.

### 7. P2: стратегия не даёт достаточного ответа о следующей технологии и объёмах

**Место:** `docs/handout.md:59–62`, `docs/development_strategy.md:5–10`.

Этапы роста, история статусов и версий описаны разумно. Но «при необходимости — колоночное хранилище» оставляет без конкретного ответа вопрос ТЗ: что идёт следом за PostgreSQL и почему. Нет даже сценарных ориентиров объёма и нагрузки. Универсальный предел PostgreSQL в строках придумывать не следует.

**Исправление:** задать сценарии с объёмом, приростом, аппаратными допущениями, числом одновременных запросов и целевым временем ответа; выбрать кандидат на следующий этап и объяснить его на конкретных запросах. Числа обозначить как гипотезы до бенчмарка, а не гарантированные пределы.

### 8. P2: пересборка core может удалить зависимые пользовательские витрины

**Место:** `model/build.sql:6–14`.

`DROP TABLE ... CASCADE` удаляет зависимые объекты, включая представления другой схемы, если они ссылаются на core. Сейчас сохранённых витрин в репозитории не обнаружено, поэтому текущие пять ответов не страдают. Но комментарий «only objects owned by this model are replaced» не описывает такое поведение; при добавлении mart/дашборда повторная сборка может удалить их определения.

**Исправление:** явно управлять зависимостями и пересоздавать витрины в том же цикле либо сохранять стабильные таблицы и транзакционно обновлять данные. До изменения архитектуры документировать ограничение CASCADE.

## Дополнительные улучшения

- P3: отделить проверки фиксированного эталонного датасета от общих инвариантов. Жёсткие числа сейчас полезны для кейса, но любое корректное расширение источника даст FAIL.
- P3: добавить CI или воспроизводимый командный прогон на PostgreSQL 16: загрузка фиксированной версии CSV, сборка, проверки, ответы и повторная сборка. Фиксировать версии, время выполнения и краткий лог.
- P3: отдельно показывать пропущенные даты у delivered и у остальных статусов. Текущий WARN на 2 966 заказов смешивает ожидаемые пропуски незавершённых заказов и дефекты фактически доставленных.
- P3: проверять сохранность ключей и значений raw/core через anti-join/EXCEPT, а не только совпадение количеств; равные количества сами по себе не доказывают отсутствие замены строк.
- P3: в setup.sh проверять код завершения `down -v`: сейчас при ошибке этой команды скрипт всё равно выводит «удалено» (`set -uo pipefail` не включает errexit).

## Порядок доработок

1. Завершить контракт дашборда и исправить ссылку защиты.
2. Сделать скачивание атомарным и проверять полноту CSV; обеспечить LF и понятный выбор Python.
3. Исправить предупреждение о переводах и NULL-безопасность контрольных сумм.
4. Связать автоматические проверки с фактическими результатами ответов, добавить недостающие проверки.
5. Выполнить и сохранить успешный полный запуск на чистом окружении; затем повторить сборку.
6. Конкретизировать технологическую стратегию и обработку зависимых витрин.

Ошибки качества исходных данных (775 заказов без позиций, один без платежа, отрицательные временные интервалы, расхождения платежей с корзиной) сами по себе не являются ошибками реализации. Их следует сохранять и объяснять; удаление таких строк ради зелёного отчёта противоречило бы подходу ТЗ.

## Статус исправлений после аудита

В следующем коммите после этого аудита добавлены атомарная загрузка CSV через временный файл, признак LF для shell-скриптов, выбор Python через `PYTHON`, проверка ошибки `docker compose down`, NULL-безопасные точные контрольные суммы и проверки среднего числа позиций и лидирующей категории.
